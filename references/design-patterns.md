# 図解見本の検索・取得・添付・照合

構成を決めるとき、画像生成へ渡すとき、生成後の確認で読む。[図解の選択](diagram-guide.md)で意味の方向性を決めてから、具体的な見本を探す。ライブラリには表紙・図解・メンバー紹介などを収録。収録件数はカタログまたは見本一覧で確認し、件数を制作ノルマにしない。

## 1. カタログを検索する

`runtime-lock.json`の`catalog`を、同じ`resolved_commit`から読む。用途の言葉を`name`、`tags`、`use_when`へ照合し、`direction`、`elements`、`information_density`で候補を絞る。検索手段がなければJSONを直接読んでよい。特定の検索スクリプトのインストールは前提にしない。

標準配置は[カタログJSON](../assets/design-patterns/catalog.json)。目で比較する場合は[見本一覧](../assets/design-patterns/index.html)でキーワード・用途・要素数を絞り、各カードのSVG・PNGと注意点を確認できる。

リポジトリを取得済みの環境では、[検索・取得ツール](../scripts/find_design_patterns.py)を使える。Python標準ライブラリだけで動き、現在の作業フォルダに依存せずスクリプト自身の場所からカタログを解決する。以下はリポジトリのルートからの実行例。

```bash
python3 scripts/find_design_patterns.py --list-directions
python3 scripts/find_design_patterns.py --direction process --elements 4 --density medium
python3 scripts/find_design_patterns.py --query "接点 循環"
python3 scripts/find_design_patterns.py --direction people --elements 4
```

条件はAND、キーワードも空白区切りのANDで検索する。`--id`はIDの完全一致、`--limit`は表示件数（通常3件）。JSONの`total`は全該当数、`results`は表示した候補。各候補には用途・要素数の意味・注意点・版・ハッシュと、確認済みの`svg_path`、画像添付用の`attachment_paths`が入る。候補なしは`total: 0`、ファイル不足やハッシュ不一致は終了コード2とエラーになる。

要素数は型ごとに意味が異なる。工程なら段階、matrixなら軸、overlapなら集合などであり、比較表の行数ではない。`element_kind`があれば確認し、`cautions`と実物を合わせて数え方を判断する。候補は通常3件以内から比較し、必要な時だけ広げる。

条件を緩める場合は元の条件との差と再設計の必要箇所を記録する。見本が合わなければ個別構成とする。カタログや素材の取得失敗は候補なしと区別し、必要な取得が未完了のまま検索・確認済みにしない。

## 2. 選んだ素材だけを取得して見る

候補の`id`、`version`、`use_when`、`cautions`、`canvas`を確認する。`assets.svg.path`と`assets.png.path`はリポジトリのルートから解決し、カタログと同じ`ref`から取得する。`sha256`があれば照合し、不一致なら使用せず取得元を確認する。キャッシュがあればリポジトリ・ref・パス・ハッシュを照合して再利用できる。

PNGを実際に開き、主従、領域の大きさ、余白、接続、重なりを見る。形状や遮蔽が重要ならSVGも確認・描画する。元ファイルを保持し、顧客用の調整は案件側の別ファイルにする。見本のID・版・ハッシュを記録する。

選定後、作業先へ1パターンだけ取り出す場合は次のように実行する。出力先は実際の案件フォルダに置き換える。

```bash
python3 scripts/find_design_patterns.py --id process-cards --output-dir /path/to/job/references
```

`出力先/process-cards/`に`preview.svg`、`preview.png`、用途・注意点・版・ハッシュを保持した`pattern.json`を保存する。取得後の`svg_path`と`attachment_paths`はこの作業先を指す。`pattern.json`の`pattern`は元のカタログ記録、`files`は取り出した素材の相対パスを表す。既存ファイルが同一なら再利用し、異なる場合は上書きせず別の出力先を求める。`--output-dir`には`--id`が必須で、検索結果全件を自動コピーしない。

顧客環境からGitHubへ直接アクセスする場合は、カタログだけを先に取得し、選んだIDの`assets.svg.path`と`assets.png.path`を同じ`ref`から取得する。この補助ツールを使うために、顧客へ全パターンの保存を要求しない。接続先・使用版・必要な顧客情報の確認はローカルの入口に従う。

ライブラリ全体の整合確認は`python3 scripts/find_design_patterns.py --validate`。全件のID重複、素材の存在、SVG・PNGのハッシュ、SVG構文、PNGの寸法を確認する。取得や検証だけで、生成ツールへ添付したことにはしない。

## 3. 原稿と顧客のデザインへ適合させる

見本から引き継ぐ特徴を具体化する。例：二領域の接点、主図に対する補足欄の幅、包含と分岐の順序。座標・列数・ラベル数は原稿に合わせる。見本のグレー、ダミー文言、サンプル数値、元のブランドは完成形の指定ではない。

顧客のHTMLで安全領域、色役割、書体、線幅、重ね方を確認する。構図見本は情報関係、顧客見本は見た目の基準として使い分ける。構図見本へ一律に「色と文字だけ参考」と指示して、採用した配置の特徴を失わせない。

精密な図解では必要なSVGを組み替え、顧客色と正式原稿を反映した配置見本を描画する。原稿へ合わせるための構図変更と、元アイコンの輪郭・縦横比を保つ処理を分ける。ロゴや精密な遮蔽はSVGの直接利用・合成で守り、画像生成だけの再現精度を保証しない。

## 4. 生成ツールへ実際に添付する

選んだ構図見本のPNG、顧客デザイン、文字入り配置見本、必要な正式素材を渡す。SVGを受け取れない場合はPNG等へ描画し、確認してから添付する。添付枚数に制限がある場合は役割の異なる見本を明示して参照シートへまとめるなど、対応できる方法を使う。

指示には各画像の役割、参照する特徴、今回の原稿と配置の変更を含める。名前やパスを書くだけで添付済みにしない。実際にツールが受け取ったファイルを[画像記録](image-request.md)に残す。添付できなければ制約を伝えて解決し、添付したものとして記録しない。

## 5. 出力と見本を並べて確認する

選定した構図、実添付、生成結果を対応させる。図から意図した関係が読めるか、配置・主従・接点・余白・要素数が残るか、別の意味に変化していないかを見る。文字の正しさだけで合格にしない。確認した特徴と残る差分・修正を記録する。

見本は生成・PPTXの完成保証ではない。顧客の固定表紙を検索結果で置き換えず、本文の構図も採用済みの局所修正では必要なく選び直さない。
